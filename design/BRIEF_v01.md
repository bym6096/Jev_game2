# GAME DESIGN BRIEF

project_id: JEV-GAME-2
version: v01 (v02 변경사항은 BRIEF_v02_delta.md 참고 — v02가 우선)

## 목표
- 이번 작업에서 해결할 문제: 판정 전용 AI 모델 Jev를 핵심에 둔, "이런 생각을 할 수 있구나" 싶을 만큼 게임다운 게임의 근본 아이디어와 핵심 메커니즘을 찾는다.
- 만들고 싶은 플레이어 경험: 인디 게임 수준에서 실제로 재미있는 게임. 설명이 매력적인 게임이 아니라 플레이할 때 재미있는 게임. 규모감 있는 턴제 게임이 출발점이었지만 장르는 확정이 아니다.
- 반드시 지키고 싶은 원칙:
  1. **Jev는 플레이어를 채점하지 않는다.** Jev는 세계 안의 존재·사물·규칙으로서 판정하고, 플레이어는 그 판정의 맥락을 바꾼다. (이전 실패 원인 참고)
  2. Jev가 없으면 만들 수 없는 경험이어야 한다. 판정을 전부 미리 계산한 표로 바꿔도 똑같은 게임이면 실패다.
  3. 재미가 먼저다. 기술 데모가 아니라 게임이어야 한다.

## Jev에 관한 사실 (웹 조사 기준, 2026-10)
- TypeSafe AI가 2026-09-15 공개한 **판정 전용 모델**. 글을 생성하지 않는다.
- 입력: 상태(state) + 형식이 정해진 질문들. 출력: 정해 둔 선택지 중 답 + **확률(신뢰도)**. 질문 유형: 선택지(choice), 점수(rubric score), 예/아니오. 정의된 선택지 밖의 답은 낼 수 없다.
- 요청 하나에 질문 여러 개를 넣으면 한 번에 답한다. 응답은 대략 70~500ms(업체·2차 자료 기준, 독립 검증 없음).
- 정확도는 최상위 LLM보다 낮다(어려운 판정 벤치마크에서 Jev 78.6% vs GPT-6 93.1%, 2차 자료).
- 요금(서드파티 자료, 공식 확인 안 됨): 입력 100만 토큰당 약 $0.042, 출력 무료. 상태 설명과 질문 문장 모두 입력에 포함. 요청당 최대 64k 토큰.
- 한도(서드파티 자료): 계정당 분당 1,200요청, 초당 25만 토큰. 동시 접속 규모에 직접 영향.
- 이미지 입력(PNG/JPEG)과 이미지 내 위치를 돌려주는 box 출력은 **실험 기능**이고 성능이 텍스트보다 낮다고 업체가 밝힘. → 이번 기획에서는 **사용하지 않는다**(디렉터 결정).
- 글이 필요하면 템플릿 문장이나 별도 LLM을 써야 한다.

## 제약
- 개발 인원: 미정 (인디 규모, 소규모 개인 개발을 가정)
- 사용 가능한 개발 시간: 미정
- 엔진 및 기술 제약: 미정. Jev API는 클라이언트에 키를 넣을 수 없으므로 실시간 호출 시 중계 서버 필요.
- 예상 플랫폼: 미정
- 제작 및 콘텐츠 범위: 인디 게임 수준
- 비용: 성능·비용이 불확실한 기능에 핵심을 걸지 않는다. 실시간 Jev 호출은 **판당 호출 수 상한**을 두어 최악 비용을 확정할 수 있어야 한다. 반복·일반 판정은 미리 계산(사전 계산 표)·캐시가 가능하면 그쪽을 쓰고, 실시간 호출은 미리 계산할 수 없는 것(플레이어가 그 판에서 만든 것, 그 판만의 역사)에 쓴다.
- 배경: **중세 판타지 같은 식상한 배경은 피한다.** 다만 이번 단계는 배경보다 핵심 메커니즘이 우선이다.

## 현재 상태
- 확정된 결정:
  - 이미지 입력 기능 제외
  - "Jev는 플레이어를 채점하지 않는다" 원칙
  - 사전 계산(기본 반응) + 상한 있는 실시간 호출(그 판만의 것) 하이브리드 방향
- 검토 중인 가설:
  - 판정 확률을 행동 전에 보여주면(input randomness) 억울함 대신 계획이 생긴다
  - 의미(semantics) 기반 판정이 손으로 설계할 수 없는 시너지를 만든다
- 아직 정하지 않은 사항: 장르, 배경, 플랫폼, 1인/다인, 엔진
- 이전 버전에서 발견된 문제:
  - 이전 프로토타입: "플레이어가 텍스트 입력 → Jev가 판단해 점수화" 구조. 판정이 곧 결과 전부라 상태·자원·연쇄가 없었고, 한 번 하고 끝나는 퀴즈가 됐다.
  - 수백 명 익명 주민을 판정하는 경영 시뮬 안(「만인의 왕국」): 확률이 읽히지 않아 유능감이 없고, 익명 다수라 애착이 없으며, 결과 후 공개라 억울함이 생김.
  - 전부 사전 계산하면 일반 게임과 구별되지 않음(디렉터 지적).

## 참고: 재미 관련 조사 요약
- 자기결정이론: 자율성·유능감·관계성 충족이 재미와 연결.
- 코스터: 재미 = 패턴 학습. 다 풀리면 지루, 안 보이면 좌절.
- 불확실성: 결과가 뻔하면 선택이 아님. 읽을 수 있는 불확실성이어야 함. 행동 전 정보(input randomness)는 계획을, 행동 후 랜덤(output randomness)은 억울함을 낳기 쉬움.
- Into the Breach(적 의도 미리 공개, 작고 촘촘함), Slay the Spire(시너지 발견), RimWorld(이야기 생성기), Frostpunk/Papers, Please(이름 있는 개인, 압박 속 선택).
- AI 게임 함정: 열린 대화는 한 번 시험해 보고 질림. 플레이어 입력이 메커니즘으로 이어질 때 몰입(1001 Nights).
- Prom Week: 사회 시뮬레이션 효과가 게이지로만 보여 와닿지 않음 → 결과는 행동으로 보여야 함.
- Disco Elysium: 이전 대화가 판정 난이도를 바꿈(호평). 단, 손으로 쓴 보정. 진행을 막는 단일 판정 실패는 좌절.

## 이번 작업 (라운드 1: 독립 탐색)
- 작업 목표: 역할별 독립 탐색. 서로의 결과를 보지 않는다.
- 필요한 산출물: 각 에이전트 시스템 프롬프트의 출력 규격을 따른 문서 1개씩
- 평가 기준: 각 에이전트 프롬프트의 성공 기준
- 이번 단계에서 하지 않을 일: 최종 후보 확정, 배경·아트 확정, 구현

# CROSS-REVIEW PROTOCOL

1. 모든 에이전트는 자신의 의견과 근거를 구분한다.
2. 다른 에이전트의 의견에 동의할 때는 동의하는 이유를 제시한다.
3. 다른 에이전트의 의견에 반대할 때는 반례, 규칙상의 근거 또는 검증 가능한 가설을 제시한다.
4. 문제를 제기한 에이전트는 문제를 발견했다는 이유만으로 수정 방향을 강제할 수 없다.
5. 시스템 설계자는 피드백을 수용 / 부분 수용 / 보류 / 기각 중 하나로 분류한다.
6. 수용하지 않은 의견은 이유와 함께 기록한다. 동일한 문제가 반복 제기되면 다시 검토한다.
7. 합의가 안 되면 쟁점을 분리하고, 가능하면 두 대안을 비교할 테스트를 설계한다.
8. 실제 테스트 결과가 기존 판단과 충돌하면 기존 판단을 수정한다.
9. 세 에이전트의 합의는 최종 결정의 필수 조건이 아니다.
10. 최종 결정과 개발 우선순위는 사람인 디렉터가 정한다.

# 우선순위 체계

| 우선순위 | 판단 기준 | 대응 |
|---|---|---|
| P0 | 핵심 재미가 성립하지 않거나 진행이 막힘 | 다음 작업 전에 검증 |
| P1 | 지배 전략, 반복 피로 등 핵심 경험을 훼손할 위험 | 초기 프로토타입에서 검증 |
| P2 | 개선 여지가 있지만 핵심 루프는 작동함 | 이후 반복 작업에서 검토 |
| P3 | 취향, 표현, 부가 기능 등 낮은 영향 | 여유가 있을 때 검토 |

테스트 전 단계에서는 P0를 단정하지 말고 "P0 가능성, 검증 필요"로 기록한다. 분류는 C가 근거를 제시하고 B가 설계 영향을 검토한 뒤 디렉터가 확정한다.
