# 측정 실행 절차서 (Runbook) v01

## 0. 개요와 역할

| 역할 | 하는 일 | 인원 |
|---|---|---|
| 작성자 | 문항·무관 기록·손 표 코드 작성, 사전 등록 | 1~2 |
| 실행자 | 파일럿, 요청 실행, 기록 | 1(작성자 겸임 가능) |
| 평가자 | 납득 평가, 블라인드 쌍비교 | 3(작성자와 다른 사람) |
| 판정자 | 판정표를 기계적으로 적용, 보고서 작성 | 1(실행자 겸임 가능) |

전체 흐름:

```
[준비] 접근 경로 확정 → 파일럿 20요청 → 문항 작성 → 사전 등록(해시)
  → [0단계] 극단 확률 4층 → 분기
  → [1단계] 엔진 공통 E2~E8 → 설정 반영
  → [2단계] 후보별 N1 / A03 / N3 / A01 → 사람 평가 → 판정
  → [보고]
```

## 1. 접근 경로 선택 (모두 미검증)

| 경로 | 설명 | 장점 | 위험·확인 사항 |
|---|---|---|---|
| P1 공식 API | 제공사(TypeSafe AI) 직접 계약·키 발급 | 모델 버전·요금 명확 | 발급 가능 여부, 약관(측정 목적 사용), 실제 한도 확인 필요 |
| P2 서드파티 모델 중계 서비스 | 여러 모델을 한 API로 중계하는 게이트웨이 | 가입이 빠를 수 있음 | **Jev가 실제로 중계되는지, 중계 시 확률 출력이 원형대로 오는지, 모델 버전이 고정되는지 확인 필요.** 서드파티 요금 자료의 출처도 여기일 수 있다(BRIEF) |
| P3 웹 플레이그라운드 | 제공사 데모 화면 | 파일럿 감 잡기 | 대량 측정 불가, 기록 수작업. **판정 근거로 쓰지 않는다** |
| P4 대체 모델 리허설 | 다른 LLM에 같은 형식(닫힌 선택지 + 확률 요청)으로 질문 | 파이프라인·문항 검증 | **결과는 Jev 판정 근거가 아니다.** 스크립트·CSV·판정 절차 점검용 |

- **권장 순서**: P4로 파이프라인 리허설(비용 거의 0) → P1 또는 P2로 파일럿 20요청 → 본 측정.
- 키는 클라이언트·저장소에 넣지 않는다. 환경 변수 또는 비밀 저장소에 둔다(BRIEF: 중계 서버 필요).

### 1.1 파일럿 20요청 체크리스트(본 측정 전 필수)
1. 선택지 밖의 답이 나오지 않는가(20/20).
2. 선택지별 확률이 반환되는가? 합이 1인가? 반환되지 않으면 **본 측정 중단**. ADE 설계 전제가 깨진다. 디렉터 보고.
3. 질문 여러 개 묶음이 한 요청으로 처리되는가.
4. 같은 요청 3회의 응답 차이(결정성 감 잡기).
5. 지연 p50, p95.
6. 요청당 토큰 수와 실제 청구액(비용 단가 검증).
7. 모델 버전 문자열을 기록할 수 있는가.

### 2.2 Jev 요청으로의 변환 예시(가상 형식, 실제 API 문서에 맞게 adapter 수정)
```json
{
  "model": "jev-<version>",
  "state": "인물: 토마. 제과점 주인. 어젯밤 밤샘 근무를 했다. 수다를 좋아한다. 오늘의 계획: 17시에 가게에서 반죽.\n지금: 17시 직전, 우체국 앞, 맑음. 들고 있는 것: 이네스의 보온병.\n오늘 보고 들은 일:\n- (조금 전, 주택가) 이네스의 보온병을 봤다.\n- (최근, 광장) 이네스가 무언가를 찾고 있는 것을 봤다.",
  "questions": [
    {"id": "ACT_next_action", "type": "choice",
     "text": "토마는 다음 시간대(17시)에 무엇을 하는가?",
     "options": ["가게에서 반죽(계획대로)", "우체국에서 수다", "광장 벤치에서 쉰다", "카페에서 커피", "집에서 낮잠", "본 물건을 챙긴다"]},
    {"id": "FACTOR", "type": "choice",
     "text": "이 선택에 가장 큰 영향을 준 것은?",
     "options": ["기록1", "기록2", "오늘의 계획", "날씨", "들고 있는 것", "없음"]}
  ]

```
- 선택지는 option_id 오름차순으로 고정하고, 문장 템플릿으로 변환한다.
- 응답에서 저장할 것: 선택지별 확률(원시), 지연, 모델 버전, 원문 응답(JSON 그대로).

## 3. 문항 작성 규칙

### 3.1 공통
1. 상황 문장은 스키마 템플릿으로만 만든다(자유 문장 금지). 페르소나는 등록된 고정 텍스트를 쓴다.
2. 한 기본 상황 = 판정자 1명 + context + log 0~3줄.
3. **조작은 log 슬롯으로만** 한다(C5-X03). context enum은 기본 상황에서 고정한다.
4. 기본 상황은 "1위가 뻔하지 않도록" 쓰려고 노력하되, 결과를 보고 고치지 않는다(사전 등록).

### 3.2 조건별 작성 규칙
| 조건 | 규칙 |
|---|---|
| C1 정확 일치 | 판정 대상과 **같은** 요소·사람·물건이 등장하는 기록 1줄 |
| C2 의미 연관 | 같은 요소는 아니지만 의미가 가까운 기록 1줄. **손 표 범주 태그로는 다른 범주**여야 한다(손 표가 범주로 잡으면 C2가 아님) |
| C3 무관(대조군) | 같은 템플릿 종류, 다른 장소·다른 인물에 관한 사실, 길이 ±20%, 판정 대상 요소와 범주 겹침 없음 |
| C4 페르소나 교체 | 같은 입력에 같은 역할의 다른 판정자 페르소나 |
| C5 누적 | 관련 기록 3줄(C1 1 + C2 2) |

### 3.3 손 표 코드
- 각 명세 7.1을 함수로 구현한다. 입력 = ADE item, 출력 = 1위 option_id. 측정 전 해시로 고정한다.

### 3.4 의미 밀도 기록
- 스키마마다 D_log, D_enum, log 조작 문항 비율을 `PREREG.md`에 적는다.

## 6. 판정 절차(기계적 적용)
1. 지표를 계산한다.
   - 변경률 = 평균(flip_vs_base)
   - Δ = 변경률(C1 또는 C2) − 변경률(C3)
   - 일치율 A = 조작 문항(C1·C2·C5)의 top1 == handtable_top1 비율
   - P = 쌍비교 다수결 Jev 승 비율
2. 판정표(ENGINE-ADE-v02 2.0~2.2, 각 명세 7.3)와 비교한다.
3. **신뢰구간 규칙**: 점추정이 "해소"여도 CI 하한이 P0 경계 아래면 "재측정"으로 둔다.
4. 재측정은 판정표의 허용 수정만 하고, 새 해시로 사전 등록 후 1회 실행한다. 두 번째도 해소에 못 미치면 P0 확정이다.
5. 판정 결과와 해석 의견을 분리해 보고한다(의견 칸).
